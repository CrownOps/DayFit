# 요구사항 정의서: 통합 일정·습관·타임테이블 관리 도구

- 작성일: 2026-07-06
- 작성 대상: Claude Code
- 요청자: 은지 (CrownOps CEO)
- 문서 목적: 개발 착수 전, 기존 앱으로 해결 가능한 범위와 커스텀 개발이 필요한 범위를 먼저 판단하고, 개발이 필요한 부분에 대해 구체적인 요구사항을 정의한다.

## 0. 결론 먼저 — "기존 앱으로 해결 가능한가?"

**부분적으로 가능하지만, 전체를 만족하는 단일 기존 앱은 없다.** 아래처럼 나눠서 판단하는 것을 권장한다.

| 요구 기능 | 기존 앱으로 충분한가 | 근거 |
|---|---|---|
| Google Calendar 일정 데이터 연동 | **예 — 일정 데이터 자체는 새로 만들 필요 없음** | Google Calendar API로 일정(제목/시간/장소)을 그대로 읽어오면 됨. |
| 일정·습관 알림(PC + 모바일) | **아니오 — 커스텀 개발 필요 (사용자 요청 반영)** | 은지님이 Google Calendar 자체 알림을 끄고 이 앱에서 PC/모바일 알림을 모두 통합해서 받길 원함. 이 경우 Google Calendar 알림에 의존할 수 없으므로, 앱이 직접 웹 푸시(Web Push)를 구현해야 함. 자세한 내용은 4.3 참고. |
| 하루 타임테이블(시간표) 시각화 | **부분 가능** | Structured, Sunsama, Motion, Reclaim.ai 등이 Google Calendar와 동기화해 하루를 시간 블록으로 보여줌. 다만 "습관 체크 + 데일리 스니펫 + 팀 토큰 사용량 + 통합 알림"까지 한 화면/한 알림 채널로 묶은 앱은 없음. |
| 습관 반복/체크/연속기록 | **부분 가능** | TickTick, Habitify 등이 이 영역은 잘 커버함. 단, Google Calendar 일정과 완전히 통합된 "하나의 하루 뷰 + 하나의 알림 채널"로 보여주진 않음. |
| 데일리 스니펫 저장/조회 자체 | **기존 시스템(GCS Pulse) 재사용 — 새로 만들 필요 없음** | 은지님이 이미 사용 중인 **GCS Pulse**(`https://github.com/Gachon-Cocone-School/gcs-pulse`)가 Daily/Weekly Snippet CRUD API를 MCP·REST 형태로 이미 제공함. 스니펫 저장소를 처음부터 새로 만들 필요 없이, 이 API를 CrownOps 팀 범위로만 호출해서 쓰면 됨. |
| 팀 헬스체크 대시보드 + 잔디(기여도 그래프) UI | **기존 앱 없음 → 이 부분만 커스텀 개발 필요** | GCS Pulse는 CrownOps만을 위한 잔디 뷰/헬스체크 대시보드를 제공하지 않으므로(교육기관 전체 플랫폼이므로), 데이터는 GCS Pulse API에서 가져오되 **CrownOps 2인 팀 전용의 얇은 프론트엔드**만 새로 만들면 됨. |
| 일일 LLM 토큰 사용량 기록 | **일부는 GCS Pulse API로 가능, 나머지는 보완 필요** | GCS Pulse MCP에 `token_usage_get`(`GET /users/me/token-usage`) API가 이미 존재함. 단 "token 역할" 권한이 필요하고, 이 API가 측정하는 사용량의 범위(GCS 프로그램 내 사용만인지, 전체 Claude 사용인지)는 확인이 필요함. 자세한 내용은 5번 섹션 참고. |

**권장 방향:** Google Calendar는 "일정 데이터"의 진실 공급원(source of truth)으로, **GCS Pulse는 "데일리 스니펫 + 토큰 사용량 데이터"의 진실 공급원**으로 사용하되, **알림만큼은 두 외부 시스템에 위임하지 않고 이 앱이 직접 책임진다.** 즉 일정·습관 모두 우리 앱의 자체 웹 푸시 알림으로 통합하고, Google Calendar의 알림 기능은 꺼서 알림이 두 군데서 중복으로 오지 않게 한다. 앱은 배포하지 않고(앱스토어 미배포), PC/모바일 브라우저에서 "홈 화면/바탕화면에 추가"하는 설치형 웹앱(PWA) 형태로 제공한다.

이 문서 이후 내용은 이 권장 방향을 기준으로 작성한다.

## 1. 프로젝트 개요

### 1.1 배경
은지님은 수업/과외/미팅 등 일정 관리, 매일 반복되는 습관 관리, 하루 흐름을 시간표처럼 보는 시각화를 하나의 도구에서 처리하고 싶어 함. 기존 캘린더 앱(목록형), 습관 앱(습관만), 시간표 앱(일정만)은 각각 한 영역만 커버해 불편함이 있었음.

### 1.2 목표
1. Google Calendar에 등록된 일정을 자동으로 가져와 하루 단위 타임테이블로 시각화한다.
2. **일정·습관 알림을 이 앱 하나로 통합한다.** Google Calendar 자체 알림은 끄고, PC와 모바일 모두에서 이 앱의 자체 웹 푸시 알림만 받는다.
3. 매일 반복되는 습관을 등록·알림·체크·연속기록(streak) 형태로 관리한다.
4. **GCS Pulse**의 Daily Snippet API를 연동해 팀(CrownOps, 현재 2인) 차원의 데일리 스니펫(일지)을 기록·조회하고, 작성 여부를 깃허브 잔디 형태로 시각화하며, 팀원 간 헬스체크를 공유한다.
5. **GCS Pulse**의 `token_usage_get` API 및 로컬 도구를 조합해, 일일 LLM(Claude 등) 토큰 사용량을 가능한 범위 내에서 기록·시각화한다.

### 1.3 비목표 (Out of Scope, 이번 단계 제외)
- 네이티브 앱스토어 배포(App Store/Play Store) — 앱은 배포하지 않고, PWA(설치형 웹앱)로만 제공
- 다중 캘린더 서비스(Outlook, Apple Calendar 등) 동시 지원 — 1차는 Google Calendar만
- 팀 규모 확장을 전제로 한 권한/조직 관리 체계 (1차는 CrownOps 소규모 팀 기준)

## 2. 사용자 및 사용 맥락

- **주 사용자**: 은지 본인 (개인 일정·습관 관리)
- **부 사용자**: CrownOps 팀원 (데일리 스니펫, 헬스체크, 토큰 사용량 공유 영역에 한함)
- **팀 범위**: 이 서비스는 **CrownOps 팀 전용**이며 외부 공개/타 팀 대상이 아니다. GCS Pulse 내 CrownOps의 특정 `team_id` 하나로만 데이터 조회 범위를 고정한다.
- **팀 규모**: 현재 2명(은지 포함)으로 시작하며, 이후 팀원이 늘어나면 `team_id`에 소속된 구성원을 추가하는 것만으로 확장 가능한 구조로 설계한다(팀원 수를 하드코딩하지 않음).
- **플랫폼**: PC 웹 + 모바일 웹을 모두 지원하는 **PWA(설치형 웹앱)**로 제공. 앱스토어에는 배포하지 않고, 사용자가 브라우저에서 "홈 화면에 추가"(모바일)/"앱으로 설치"(PC 크롬 등)를 통해 아이콘으로 접근한다. 알림은 이 PWA를 기반으로 한 웹 푸시로 PC와 모바일 양쪽에 동일하게 전달한다(4.3 참고).

## 3. 기능 요구사항

### 3.1 모듈 A — 일정 관리 & Google Calendar 연동
| ID | 요구사항 | 비고 |
|---|---|---|
| A-1 | Google OAuth로 사용자의 Google Calendar 계정 연결 | Google Calendar API 사용 |
| A-2 | 연결된 캘린더에서 일정(제목, 시작/종료 시각, 장소, 설명) 읽어오기 | `events.list` |
| A-3 | 앱 내에서 새 일정 생성 시 Google Calendar에도 동시 생성 | `events.insert`, 양방향 동기화 |
| A-4 | 일정 수정/삭제 시 Google Calendar와 동기화 | `events.patch` / `events.delete` |
| A-5 | Google Calendar 자체 알림(팝업/이메일/모바일 푸시)은 끄고, 알림은 이 앱의 자체 웹 푸시로만 발송 | 자세한 내용은 4.3, 모듈 F 참고. Calendar API로 동기화하는 이벤트는 `reminders: {useDefault: false, overrides: []}`로 설정해 Calendar 앱에서 중복 알림이 뜨지 않게 함 |
| A-6 | 일정 생성/수정 시 "N분 전 알림" 옵션을 앱 UI에서 설정 → 앱 자체 알림 스케줄러(모듈 F)에 등록 | Calendar의 `reminders` 필드가 아니라 우리 서버의 알림 스케줄에 저장 |

### 3.2 모듈 B — 하루 타임테이블 뷰
| ID | 요구사항 | 비고 |
|---|---|---|
| B-1 | 하루를 세로/가로 타임라인으로 시각화 (예: 09:00–10:00 준비, 10:00–12:00 과외 …) | 09:00~24:00 기본, 스크롤로 전체 24시간 |
| B-2 | Google Calendar 일정 + 습관(모듈 C) + 데일리 스니펫 작성 여부를 한 화면에 병합 표시 | 색상/아이콘으로 유형 구분 |
| B-3 | 빈 시간대(공백) 강조 표시 — 일정이 없는 구간을 시각적으로 구분 | |
| B-4 | 일/주 단위 전환 뷰 | 1차는 일 단위 우선 구현, 주 단위는 2차 |
| B-5 | 타임테이블 항목 클릭 시 상세/수정 화면으로 이동 | |

### 3.3 모듈 C — 습관 관리
| ID | 요구사항 | 비고 |
|---|---|---|
| C-1 | 습관 등록 (이름, 목표 시간대, 반복 주기: 매일/특정 요일) | |
| C-2 | 설정된 시간에 앱 자체 웹 푸시로 알림 발송 (PC + 모바일) | Google Calendar에 위임하지 않음 — 모듈 F 참고 |
| C-3 | 완료 체크(체크박스/토글) | |

| C-5 | 놓친 습관(그날 체크 안 된 항목) 별도 목록으로 표시 | |
| C-6 | 습관별 월간 완료율 통계 | 그래프 또는 히트맵 |

### 3.4 모듈 D — 데일리 스니펫(GCS Pulse 연동) & 팀 헬스체크 & 잔디

**설계 원칙**: 스니펫 데이터는 자체 DB에 새로 저장하지 않고, **GCS Pulse API를 통해 읽고 쓴다.** 우리 앱은 GCS Pulse 위에 CrownOps 전용 뷰(잔디, 헬스체크 대시보드)를 얹는 얇은 레이어 역할만 한다.

#### GCS Pulse 연동 정보
- 리포지토리: `https://github.com/Gachon-Cocone-School/gcs-pulse`
- MCP 엔드포인트: `https://api.1000.school/mcp` (streamable HTTP), 인증: `Authorization: Bearer <API_TOKEN>`
- 동일 엔드포인트가 REST API로도 매핑되어 있어(예: `POST /daily-snippets`, `GET /daily-snippets`), 백엔드에서 MCP 대신 REST를 직접 호출해도 무방함 — 백엔드 아키텍처에 맞는 쪽으로 Claude Code가 선택.
- 인증 방식상 **팀원 각자가 자신의 GCS Pulse `API_TOKEN`을 보유**해야 하며, 우리 서버는 사용자별 토큰을 암호화 저장 후 해당 사용자로서 API를 호출한다(4.4 참고).
- 이 서비스는 **CrownOps `team_id` 하나로 스코프를 고정**한다. 팀원이 아닌 GCS Pulse 사용자의 데이터는 절대 조회하지 않는다.

#### 기능 요구사항
| ID | 요구사항 | 비고 |
|---|---|---|
| D-1 | 매일 짧은 일지(스니펫) 작성 폼 — 자유 텍스트 + 선택적 태그(오늘 한 일/블로커/컨디션) | GCS Pulse `daily_snippets_create` (`POST /daily-snippets`) 호출로 저장 |
| D-2 | 팀원별 스니펫을 CrownOps `team_id` 범위로만 조회 | `daily_snippets_list` (`GET /daily-snippets`)에 팀/기간 필터 적용 — 필터 파라미터명은 GCS Pulse API 스펙 확인 필요(9번 Open Question 참고) |
| D-3 | 스니펫 작성/수정 | `daily_snippets_update` (`PUT /daily-snippets/{id}`), `daily_snippets_delete` (`DELETE /daily-snippets/{id}`) |
| D-4 | 스니펫에 컨디션/헬스 체크 항목 포함 (예: 컨디션 1–5점, 수면시간, 특이사항) | GCS Pulse 스니펫 스키마에 전용 필드가 없다면, 자유 텍스트 안에 구조화된 태그(`#컨디션:4`)로 넣거나 `content`에 포함하는 절충안 필요 — 스키마 확인 후 결정 |
| D-5 | 팀 헬스체크 대시보드 — 팀원 2명(이후 N명)의 오늘 컨디션을 한눈에 확인 | GCS Pulse에서 가져온 스니펫을 파싱해 CrownOps 전용 화면에서 렌더링(신규 개발 영역) |
| D-6 | 깃허브 잔디(contribution graph) 형태의 히트맵 — 하루라도 스니펫을 작성했으면 칸이 채워짐 | `daily_snippets_list`로 날짜별 존재 여부만 뽑아 프론트에서 히트맵 렌더링(신규 개발 영역). 개인별 + 팀 전체 뷰 모두 제공 |
| D-7 | 팀원이 늘어나도 코드 변경 없이 반영되는 구조 | 팀원 목록을 하드코딩하지 않고 `team_id` 기준 조회 결과를 그대로 순회 |
| D-8 | (선택) Comment/멘션 기능 활용 — 팀원 스니펫에 `@이름`으로 댓글 남기기 | GCS Pulse `comments_create` 등 이미 제공됨, 필요 시 재사용 |
| D-9 | (선택) 슬랙 연동 — 스니펫 작성/미작성 리마인드 | Slack MCP 이미 연결되어 있음, 활용 가능. GCS Pulse 자체 알림(`notifications_*`)도 대안으로 검토 가능 |

### 3.5 모듈 F — 통합 알림 시스템 (PC + 모바일 웹 푸시)

이번 요청에서 가장 핵심적인 변경사항. Google Calendar 알림을 끄고, 일정과 습관 알림을 전부 이 앱의 자체 웹 푸시로 통합한다.

| ID | 요구사항 | 비고 |
|---|---|---|
| F-1 | PWA 설치 시 알림 권한 요청 및 Web Push 구독(subscription) 등록 | 브라우저 표준 Push API(발송 계층은 FCM 또는 자체 VAPID) + 서비스워커 사용, PC/모바일 모두 동일 메커니즘 |
| F-1a | **최초 실행 시 "홈 화면에 추가" 안내 화면을 필수로 노출** (아이폰 사용자 대상 — 설치 전에는 알림 자체가 불가능) | 4.3 참고 |
| F-2 | 한 사용자가 여러 기기(PC + 폰)에서 각각 설치/구독하면, 알림이 등록된 모든 기기로 동시에 발송 | 기기별 subscription을 모두 저장 (모듈 F 데이터 모델 참고) |
| F-3 | 서버에서 주기적으로(예: 1분마다) 다가오는 일정/습관을 확인해 알림 시각이 된 항목을 찾아 발송 | 백그라운드 스케줄러(cron 또는 큐) 필요 |
| F-4 | 일정 알림: 사용자가 지정한 "N분 전"에 발송 | A-6 참고 |
| F-5 | 습관 알림: 습관별로 설정한 시각에 발송 | C-2 참고 |
| F-6 | 알림 클릭 시 앱의 해당 일정/습관 화면으로 바로 이동(딥링크) | 서비스워커의 `notificationclick` 이벤트 처리 |
| F-7 | Google Calendar 쪽 알림은 동기화 시 명시적으로 끄기 (A-5) | 이미 존재하는 기존 일정들도 최초 연동 시 일괄로 알림 끄기 처리 필요 — 사용자의 기존 캘린더 데이터를 수정하는 작업이므로 최초 1회 동의를 받고 진행 |
| F-8 | 알림 발송 실패/구독 만료(expired subscription) 처리 — 만료된 기기는 자동으로 구독 목록에서 정리 | Web Push 표준 동작(410 Gone 등) 처리 |

**확정된 사실 — 아이폰 알림의 필수 전제조건**: 아이폰(iOS Safari 16.4+)에서는 **반드시 "홈 화면에 추가"로 설치된 PWA 상태에서만** 푸시 알림이 동작한다. 이는 애플 WebKit 엔진의 정책이라 FCM 등 어떤 푸시 서비스를 쓰든 우회할 수 없다(자세한 근거는 4.3 참고). 브라우저 탭으로만 열어둔 상태로는 알림이 오지 않는다. 안드로이드/PC는 설치 없이도 동작하지만, 경험을 통일하기 위해 모든 플랫폼에서 설치를 권장한다.

### 3.6 모듈 E — 일일 LLM 토큰 사용량 기록
자세한 실현 가능성 분석은 5번 섹션 참고. GCS Pulse에 이미 `token_usage_get`(`GET /users/me/token-usage`) API가 존재하는 것이 확인되었으나, 이 데이터가 정확히 무엇을 측정하는지(전체 Claude 사용량인지, GCS 프로그램 내 활동만인지) 확인이 필요해 1차는 "GCS Pulse API + 보완 수단"을 병행하는 수준으로 정의한다.

## 4. 비기능 요구사항

### 4.1 데이터 저장
- 개인 데이터(일정 캐시, 습관, 개인 스니펫)와 팀 공유 데이터(팀 스니펫, 헬스체크, 토큰 사용량 집계)를 분리해서 설계.
- Google Calendar가 일정의 원본(source of truth)이므로, 앱 DB에는 캐시만 저장하고 주기적으로 재동기화.

### 4.2 성능
- 타임테이블 뷰 로딩 3초 이내 (Google Calendar API 응답 지연 고려해 로컬 캐시 우선 표시 후 백그라운드 동기화 권장).

### 4.3 알림/푸시 — 확정된 방향: 자체 웹 푸시(PC + 모바일, iOS 포함)
이전 검토에서는 Google Calendar 알림에 위임하는 안을 권장했으나, **은지님이 "Google Calendar 알림은 끄고 이 앱 하나에서 PC/모바일 알림을 모두 받고 싶다"고 명확히 요청**해, 아래와 같이 방향을 확정한다. 은지님 폰은 아이폰으로 확인됨.

| 방식 | 채택 여부 | 설명 |
|---|---|---|
| **웹 푸시(PWA, Web Push API — 발송 계층은 FCM 또는 자체 VAPID)** | **채택** | 앱을 배포하지 않는 대신, PC/모바일 브라우저에서 "앱으로 설치"(홈 화면/바탕화면에 추가)한 PWA 상태로 서비스워커를 통해 푸시를 발송한다. |
| Google Calendar 알림 | **끔** | 이 앱이 유일한 알림 채널이 되도록, 동기화되는 일정의 Calendar 알림은 명시적으로 끈다(A-5, F-7 참고). |
| 네이티브 앱(iOS/Android) + FCM/APNs 직접 연동 | 채택 안 함 | 앱스토어 배포를 하지 않기로 했으므로 해당 없음. |

#### FCM을 쓰면 아이폰의 "홈 화면 추가" 제약이 없어지는지 — 확인 결과: 아니오
FCM(Firebase Cloud Messaging)을 발송 서버로 써도 **아이폰의 홈 화면 설치 요구사항은 사라지지 않는다.** 이유는 이 제약이 "어떤 푸시 서비스를 쓰느냐"가 아니라 **애플 WebKit/Safari 엔진 자체의 정책**이기 때문이다.

- iOS(16.4 이상)는 Push API를 오직 "홈 화면에 추가되어 standalone 모드로 실행 중인 웹앱"에만 열어준다. Safari 브라우저 탭 상태에서는 `navigator.serviceWorker.register()` 이후에도 `pushManager`가 아예 존재하지 않는다.
- iOS에서는 Chrome/Firefox 등 다른 브라우저도 내부적으로 WebKit 엔진을 강제로 사용하므로("iOS 브라우저는 전부 WebKit"이라는 애플 정책), 브라우저를 바꿔도 이 제약은 동일하게 적용된다.
- FCM의 웹 푸시 SDK를 아이폰(Safari)에 적용해도, 실제 알림 전달은 결국 Apple Push Notification service(APNs)를 거쳐서 이뤄진다. FCM은 이 위에 얹힌 "발송 편의 레이어"(안드로이드/웹/iOS를 하나의 API로 통합 발송)일 뿐, OS 차원의 설치 요구사항 자체를 우회해주지는 않는다.
- 즉, **네이티브 iOS 앱(App Store 배포 + APNs 직접 연동)을 만들지 않는 한, "홈 화면에 추가"는 아이폰에서 피할 수 없는 필수 단계**다. 이번 프로젝트는 앱스토어 미배포를 전제로 하므로, 이 단계는 그대로 온보딩에 포함한다.

**결론 및 권장**: FCM을 발송 계층으로 채택하는 것은 나쁘지 않은 선택이다(PC/안드로이드/아이폰을 하나의 API로 통합 발송할 수 있어 서버 코드가 단순해짐, Firebase 콘솔로 발송 상태 확인 가능). "아이폰은 홈 화면에 추가해야만 알림이 온다"는 제약은 FCM 채택 여부와 무관하게 유지되지만, **이 서비스는 판매용이 아니라 CrownOps 2인 팀 자체 사용 목적이므로 이 설치 절차는 문제 되지 않는 것으로 확정함.** 첫 실행 시 "홈 화면에 추가해주세요" 안내 화면을 필수 온보딩 단계로 넣는다(F-1a, 3.5 모듈 F 참고).

#### 구현 방식 요약
1. FCM 프로젝트 생성 + 웹 푸시용 VAPID 키 발급 (Firebase 콘솔에서 발급, `web-push` 라이브러리로 직접 관리하는 대안도 가능).
2. 사용자가 PWA를 설치(iOS는 필수, PC/안드로이드는 권장)하고 알림 권한을 허용하면, FCM JS SDK가 구독 토큰을 발급 → 서버에 저장.
3. 서버는 스케줄러(예: 매 1분 cron)로 "지금 알림을 보내야 할 일정/습관"을 조회하고, 해당 사용자의 모든 등록 기기(PC + 아이폰 등 여러 기기 가능)에 FCM Admin SDK로 푸시 전송.
4. 서비스워커가 `push`(또는 FCM의 `onBackgroundMessage`) 이벤트를 받아 OS 알림으로 표시하고, 클릭 시 앱의 해당 화면으로 이동.

**아이폰(iOS) 관련 제약 — 반드시 확인 필요**: iOS Safari는 16.4 버전부터 웹 푸시를 지원하지만, **반드시 "홈 화면에 추가"로 설치한 PWA 상태에서만** 동작한다. 브라우저 탭으로만 열어둔 상태로는 알림이 오지 않는다. 안드로이드/PC는 이런 제약이 없다. 은지님과 팀원의 폰 OS를 확인해, 아이폰이라면 "설치" 과정을 온보딩에 명확히 포함해야 한다(9번 Open Question).

### 4.4 보안/권한
- Google OAuth 토큰은 서버 사이드에 암호화 저장.
- GCS Pulse `API_TOKEN`도 팀원별로 서버 사이드에 암호화 저장하며, 코드/저장소에 커밋하지 않는다(GCS Pulse 문서의 보안 권장사항과 동일).
- 팀 공유 데이터(스니펫, 헬스체크, 토큰 사용량)는 CrownOps 팀원 인증된 사용자만 조회 가능하며, 조회 범위는 항상 CrownOps `team_id`로 고정한다.

## 5. LLM 토큰 사용량 — API로 자동 수집이 가능한가? (요청하신 판단)

결론: **완전 자동화는 어렵고, 계층별로 가능한 정도가 다르다.** 다만 GCS Pulse에 이미 관련 API가 존재하는 것이 확인되어, 이를 1순위 후보로 검토한 뒤 나머지 방법을 보완책으로 정리한다.

### 5.0 GCS Pulse `token_usage_get` API (1순위 검토 대상)
- GCS Pulse MCP 매뉴얼에 `token_usage_get` 툴이 `GET /users/me/token-usage` 엔드포인트에 매핑되어 있는 것이 확인됨.
- 접근 조건: 문서상 **"token 역할"**이 부여된 사용자만 호출 가능하다고 명시되어 있음. 은지님과 팀원 계정에 이 역할이 이미 있는지, 없다면 어떻게 부여받는지 확인이 필요함(Open Question).
- **알 수 없는 부분(중요)**: 이 API가 반환하는 "토큰 사용량"이 (a) GCS 코호트 프로그램 안에서의 Claude 사용만 집계한 것인지, (b) 사용자의 Claude 계정 전체(개인 API 키, Claude Code, claude.ai 등) 사용량을 집계한 것인지는 리포지토리의 README/MCP 매뉴얼만으로는 확정할 수 없음. 실제 호출해보거나 GCS Pulse 운영진(김남주 등 커밋 이력에 등장하는 관리자)에게 문의해 범위를 확인하는 것이 첫 단계로 필요함.
- 만약 (a)라면, CrownOps 업무 전반의 토큰 사용량(예: DentalSync 개발에 쓴 Claude Code 사용량 등)까지는 못 잡을 가능성이 높으므로, 5.2의 로컬 도구 방식과 병행이 필요하다.
- 만약 (b)라면, 이 API 하나로 팀 토큰 사용량 자동 집계가 사실상 해결되므로 5.1~5.3의 대안들은 참고용으로만 남겨도 된다.

**권장 조치**: 개발 착수 전, `token_usage_get` 호출 테스트를 먼저 해보고 반환 필드(범위·기간·모델 구분 여부)를 확인한 뒤 모듈 E의 최종 설계를 확정한다. 아래 5.1~5.3은 이 API만으로 충분하지 않을 경우의 보완책이다.

### 5.1 Anthropic 공식 Usage & Cost API
- Anthropic은 조직 단위 사용량을 조회하는 `/v1/organizations/usage_report/messages`, 비용 조회용 `/v1/organizations/cost_report` 엔드포인트를 제공한다. 모델·워크스페이스·서비스 티어별로 시간 단위(분/시/일)로 집계된 데이터를 받을 수 있다.
- **단, 이 API는 "Admin API 키"가 있어야 호출 가능하다.** 일반 API 키로는 접근할 수 없고, 조직 관리자 권한이 필요하다.
- 개인 사용자별(팀원 한 명 한 명) 구분은 API 키를 팀원별로 분리 발급했을 때만 `group_by`로 나눠볼 수 있다. 팀원들이 같은 API 키를 공유하거나 각자 Claude.ai 구독(Pro/Max)만 쓰고 있다면 이 API로는 개인별 사용량을 볼 수 없다.
- Enterprise 플랜에는 사용자 단위(named user) 비용/사용량까지 보여주는 별도의 **Enterprise Analytics API**가 있지만, Enterprise 플랜 전용이라 소규모 팀에는 해당하지 않을 가능성이 높다.

### 5.2 Claude Code(터미널)를 쓰는 경우 — 더 현실적인 방법
- Claude Code는 Pro/Max 구독이든 API든 상관없이, 로컬에 `~/.claude/projects/` 경로에 세션별 JSONL 로그 파일로 토큰 사용 내역을 남긴다.
- `ccusage`, `Claude-Code-Usage-Monitor` 같은 오픈소스 CLI 도구가 이 로컬 로그를 읽어서 일별/모델별 토큰 사용량과 예상 비용을 계산해준다. Admin API 키도 필요 없고 네트워크 호출도 없다.
- 이 방식이 **팀원 개인의 Claude Code 사용량을 가장 쉽게, 무료로 얻을 수 있는 방법**이다.
- 제약: 각 팀원의 로컬 컴퓨터에서 실행해야 하므로, "자동으로 서버에 모이는" 구조를 만들려면 각 팀원이 (a) 로컬에서 CLI 실행 → JSON/CSV로 내보내기 → (b) 우리 앱에 업로드하는 반자동 흐름이 필요하다. 완전 무인 자동화를 원하면 각 팀원 PC에 스케줄러(cron 등)를 심어야 하는데, 이건 팀원 로컬 환경 접근이 필요해 현실적으로 번거롭다.
- Claude Code는 `CLAUDE_CODE_ENABLE_TELEMETRY=1` 환경변수로 OpenTelemetry 지표를 자체 서버로 내보낼 수도 있다. 이 경우 팀 전체가 하나의 OTLP 수집 서버(예: 우리가 만든 작은 백엔드)로 실시간 전송하는 것이 가능하다. 이 방식이 **가장 자동화에 가깝지만**, 각 팀원의 Claude Code 설정에 환경변수를 세팅해야 한다는 전제가 붙는다.
- claude.ai 웹/앱 채팅(터미널이 아닌 일반 대화)의 개인별 토큰 사용량은 위 방법들로 잡히지 않는다(로컬 로그가 없음). 이 부분은 사실상 자동 수집 방법이 없다.

### 5.3 권장 설계 (현실적 절충안)
0순위: **GCS Pulse `token_usage_get` 호출 테스트부터 한다.** 반환 데이터가 요구사항을 충족하면 5.1~5.2는 불필요해진다.

0순위 확인 후에도 부족한 부분이 있다면, 1차는 **수동/반자동 입력을 기본으로 설계**한다.
- 팀원이 매일 데일리 스니펫 작성 시, `ccusage` 등으로 확인한 "오늘 사용량" 숫자를 직접 입력하는 필드(E-6)를 제공.
- 원하면 추가로 `ccusage --json` 결과를 붙여넣기만 하면 파싱해서 자동으로 필드를 채워주는 소형 파서를 앱에 내장 (수동 실행 + 반자동 파싱 조합).

2차 고도화(선택, 팀 규모/예산 여유 있을 때):
- Admin API 키를 발급받을 수 있는 조직 구조라면, 서버에서 매일 배치로 `/v1/organizations/usage_report/messages`를 호출해 조직 전체 합산치를 가져와 팀 대시보드에 표시. (개인별 구분은 API 키를 팀원별로 나눠 발급해야 가능)
- 팀원들이 동의하면 Claude Code에 텔레메트리(OTLP)를 설정해 우리 백엔드로 실시간 전송받는 구조로 전환.

**요약하면, GCS Pulse의 `token_usage_get`이 범위를 충분히 커버하는지가 관건이며, 이를 먼저 검증한 뒤 부족한 부분만 반자동(로컬 도구 + 수동/붙여넣기 입력) 방식으로 보완하는 것을 권장한다. 팀이 커지거나 Admin/Enterprise 권한이 생기면 그 다음 자동화 단계로 넘어간다.**

## 6. 제안 기술 스택 (참고용, Claude Code가 조정 가능)

- 프론트엔드: Next.js (PWA 지원, 서비스워커), React

- 외부 연동: Google Calendar API, **GCS Pulse API/MCP**(`https://api.1000.school/mcp`, 데일리 스니펫 및 토큰 사용량용), (선택) Slack API, (선택) Anthropic Admin API
- 배포: Vercel/Railway (기존 CrownOps 스택 재사용 가능)

## 8. 단계별 로드맵 (MVP 우선순위)

1. **MVP 1단계**: Google Calendar 연동 + 하루 타임테이블 뷰 + PWA 설치/웹 푸시 인프라(구독 등록, VAPID) 구축 (모듈 A, B, F-1~F-2)
2. **MVP 2단계**: 일정·습관 알림 스케줄러 완성 (Google Calendar 알림 끄기 포함) + 습관 등록/체크/streak (모듈 C, F-3~F-8)
3. **MVP 3단계**: GCS Pulse 연동(팀원별 `API_TOKEN` 세팅) + 데일리 스니펫 작성/조회 + 잔디 시각화 (모듈 D의 D-1, D-2, D-6)
4. **확장 1**: 팀 헬스체크 대시보드 (D-4, D-5) + 선택적 댓글/슬랙 리마인드 (D-8, D-9)
5. **확장 2**: `token_usage_get` 테스트 및 반영, 부족한 부분은 수동/반자동 입력으로 보완 (모듈 E, 5.0~5.3)
6. **확장 3(선택)**: Admin API 기반 토큰 사용량 자동 집계

## 9. 착수 전 은지님 확인이 필요한 사항 (Open Questions)

1. ~~홈 화면 추가 설치가 괜찮은지~~ → **확정됨.** 판매용 제품이 아니라 CrownOps 자체 사용 목적이므로, 아이폰에서 "홈 화면에 추가" 온보딩 단계(F-1a)가 있어도 무방함. 팀원 1명의 폰 OS가 아이폰이라면 동일하게 적용, 안드로이드라면 설치는 선택사항으로 안내.
2. FCM을 발송 계층으로 채택하는 데 동의하는지 (Firebase 프로젝트를 CrownOps 명의로 새로 만들어야 함), 아니면 자체 VAPID 키 방식을 선호하는지?
3. **CrownOps의 GCS Pulse `team_id` 값**은 무엇인지 (개발 착수 시 필요).
4. **팀원 2명 각각의 GCS Pulse `API_TOKEN`**을 어떻게 발급/전달받을지 (본인이 GCS Pulse 계정 설정에서 직접 발급하는 방식인지 확인).
5. `token_usage_get` API(`GET /users/me/token-usage`) 호출 권한("token 역할")이 두 팀원 계정에 이미 있는지, 없다면 누구에게 요청해야 하는지?
6. `token_usage_get`이 반환하는 사용량 범위가 GCS 프로그램 내 활동만인지, 전체 Claude 사용량인지 — 실제 호출 테스트로 먼저 확인 필요.
7. GCS Pulse 데일리 스니펫 스키마에 "컨디션 점수/수면시간" 같은 헬스체크 전용 필드가 이미 있는지, 없다면 자유 텍스트/태그로 대체할지 여부.
8. 팀 토큰 사용량 중 GCS Pulse API로 못 채우는 부분은 팀원들이 매일 `ccusage` 등을 직접 실행해 숫자를 붙여넣는 반자동 방식으로 보완해도 괜찮은지?
9. 1차 개발 범위를 개인용(은지 본인, 모듈 A/B/C/F)으로 먼저 좁히고, 팀 기능(D, E)은 2차로 미룰지, 처음부터 함께 개발할지?
10. 최초 연동 시 **기존 Google Calendar 일정들의 알림을 앱이 일괄로 꺼도 되는지** 동의 확인 (F-7 참고 — 기존 캘린더 데이터를 수정하는 작업이므로).
